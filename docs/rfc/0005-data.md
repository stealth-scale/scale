# RFC-0005: The data foundation

## Summary

An application reads and changes the data behind its pages through one foundation,
`@stealthscale/provider-data`. It covers:

- Operations the gateway publishes, named by id and typed
- A transport that sends them with the person's token
- One query client per page, and per request on a server, that caches the data of every query
- Mutations that apply at once and roll back when the service refuses
- Invalidation by resource, driven by the application's own changes and by a stream of changes from
  the services
- Route loaders that load a page's data with its code
- Server rendering that streams each query's data into the page

The foundation builds on TanStack Query and exports its API. It adds what the library leaves to its
user: the operation, the transport, the error model, invalidation by resource, the changes stream,
and the reset on a change of person or tenant.

## Motivation

### The requirements

- A page's data loads in parallel with its code, when the person points at a link.
- Components that read the same data share one request and one cache entry.
- The browser sends only operations the product published, by id, with the person's token.
- A change the person makes shows at once, and rolls back with a readable error when the service
  refuses it.
- A retried change applies once. A change to a record that someone else changed first is refused as
  a conflict.
- A change made anywhere, by another person, in another tab or by another service, shows on every
  page that displays the record, without a reload.
- A refusal renders under the form field it refuses, as the not-found page, as the sign-in page or
  as a message, by its kind.
- A server-rendered page's first render in the browser reuses the data the server fetched.
- The server does not write an error's details into the page.
- One person's or tenant's data never renders for another after a sign-out or a tenant switch.
- A page shows that it is offline, and the changes made offline are sent once it is online again.
- A page runs in development and in tests without a service, from samples.

### Why this layer

- The router leaves freshness to the query client. A preloaded route never counts as fresh on its
  own (`foundations/providers/router/src/defaults.ts:11-13`). The router's declarations have no
  loader until this foundation states what a loader reads (RFC-0006).
- `Shell` renders no data client, so an application without data bundles none
  (`foundations/providers/shell/src/shell.tsx:96-98`). This foundation is a provider the application
  renders inside `Shell`, beside its router.
- TanStack Query caches data by key, removes duplicate requests, retries, refetches on focus and on
  reconnection, runs mutations with optimistic updates, pauses while offline, and dehydrates for
  server rendering. TanStack Router's server integration builds on it. The foundation adds what the
  library leaves to its user, and renames nothing the library names.

## Detailed design

### The package

| Package                       | Directory                    | Depends on                                                     | Contains                                                                                     |
| ----------------------------- | ---------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `@stealthscale/provider-data` | `foundations/providers/data` | `@tanstack/react-query` 5.104.0 and React as peers             | Operations, the transport, the client, queries, mutations, errors, resources, changes, hooks |
| its `./router` entry          | the same                     | `@tanstack/react-router-ssr-query` 1.167.3 as an optional peer | The router's context, route loaders, and the server integration                              |
| its `./testing` entry         | the same                     | nothing further                                                | The sampled transport and the test client                                                    |

- The package exports a curated list of TanStack Query's names, typed as the library types them:
  `useQuery`, `useSuspenseQuery`, `useQueries`, `useSuspenseQueries`, `useInfiniteQuery`,
  `useSuspenseInfiniteQuery`, `useMutation`, `useMutationState`, `useIsFetching`, `useIsMutating`,
  `useQueryClient`, `queryOptions`, `infiniteQueryOptions`, `skipToken`, `keepPreviousData`,
  `onlineManager` and the `QueryClient` type. A component reads data with the library's own hooks
  over the options this foundation builds.
- `@tanstack/react-router-ssr-query` 1.167.3 requires `@tanstack/query-core` and
  `@tanstack/react-query` 5.102.0 or later, and `@tanstack/react-router` 1.170.33 or later. The
  repository installs the router at 1.170.34.
- The package does not import a GraphQL client. An operation is sent by its id, so the browser never
  parses a document, and TanStack Query is the cache.

### Operations

An operation is a name the gateway runs. Its data and its variables are in the type alone.

```ts
/**
 * Lists the kinds of operation.
 */
export type OperationKind = "mutation" | "query" | "subscription";

/**
 * Types an operation that takes no variables.
 */
export type NoVariables = Readonly<Record<string, never>>;

/**
 * Names one operation the gateway publishes, with its data and its variables in the type alone.
 */
export interface Operation<
  Data = unknown,
  Variables extends object = NoVariables,
  Kind extends OperationKind = OperationKind,
> {
  /**
   * Types of the operation's data and variables, for the type checker alone.
   */
  readonly "~types"?: { readonly data: Data; readonly variables: Variables };

  /**
   * The id the gateway runs the operation under: `<application>~<version>~<hash>`.
   */
  readonly id: string;

  /**
   * Whether the operation reads, changes or streams.
   */
  readonly kind: Kind;
}

/**
 * Defines a query, an operation that reads.
 */
export function defineQuery<Data, Variables extends object = NoVariables>(
  id: string,
): Operation<Data, Variables, "query">;

/**
 * Defines a mutation, an operation that changes records.
 */
export function defineMutation<Data, Variables extends object>(
  id: string,
): Operation<Data, Variables, "mutation">;

/**
 * Defines a subscription, an operation whose data arrives as a stream of events.
 */
export function defineSubscription<Data, Variables extends object = NoVariables>(
  id: string,
): Operation<Data, Variables, "subscription">;
```

```ts
export const requestById = defineQuery<RequestData, { readonly id: string }>("time-off~4~9c1e7a");

export const approveRequest = defineMutation<ApproveData, ApproveVariables>("time-off~4~41b0d2");
```

- The gateway runs only the documents a product published. The browser sends the id, never a
  document's text, so a page cannot run an operation nobody reviewed.
- The id is opaque to the foundation. A build that hashes the documents writes the ids, and an
  operation module exports one `define*` call per document.
- An operation's variables are JSON, because they are part of the cache key and of the request body.
- The types are written by hand until the gateway's schema generates them (see "Unresolved and
  future work").

### The transport

The transport sends an operation and returns its data. The client runs every operation through one
transport.

```ts
/**
 * Lists what one run of an operation may state beside its variables.
 */
export interface RunOptions {
  /**
   * Key that makes a retried mutation apply once. The foundation sets it for every mutation.
   */
  readonly idempotencyKey?: string | undefined;

  /**
   * Signal that cancels the request.
   */
  readonly signal?: AbortSignal | undefined;
}

/**
 * Sends operations to the service that runs them.
 */
export interface Transport {
  /**
   * Runs a query or a mutation, and resolves with its data.
   *
   * @throws {@link DataError} When the request fails or the service refuses it.
   */
  readonly run: <Data, Variables extends object>(
    operation: Operation<Data, Variables, "mutation" | "query">,
    variables: Variables,
    options?: RunOptions,
  ) => Promise<Data>;

  /**
   * Calls `next` with the data of each event of a subscription until the signal aborts, and
   * resolves when the stream ends.
   *
   * @throws {@link DataError} When the stream cannot open or ends with an error.
   */
  readonly subscribe: <Data, Variables extends object>(
    operation: Operation<Data, Variables, "subscription">,
    variables: Variables,
    next: (data: Data) => void,
    signal: AbortSignal,
  ) => Promise<void>;
}
```

`gatewayTransport` sends operations to the gateway:

```ts
/**
 * Lists what the gateway transport is created from.
 */
export interface GatewayOptions {
  /**
   * The fetch it sends requests with. The global one where left out.
   */
  readonly fetch?: typeof fetch | undefined;

  /**
   * Milliseconds a request may take before it fails as `network`. 30,000 by default.
   */
  readonly timeout?: number | undefined;

  /**
   * Returns the person's token, or undefined for nobody. `renew` is true after the gateway refused
   * the last token.
   */
  readonly token: (renew: boolean) => Promise<string | undefined>;

  /**
   * Address of the gateway.
   */
  readonly url: string;
}

/**
 * Creates the transport that sends operations to the gateway by their ids.
 */
export function gatewayTransport(options: GatewayOptions): Transport;
```

| Request         | Sent as                                                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Query, mutation | `POST` to `url` with the JSON body `{ "documentId": id, "variables": { … } }` and `Accept: application/graphql-response+json, application/json` |
| Every request   | `Authorization: Bearer <token>` where `token` returns one                                                                                       |
| Mutation        | `Idempotency-Key: <key>`, one key per call, the same on each retry                                                                              |
| Subscription    | The same body with `Accept: text/event-stream`. Each `next` event contains one execution result, and a `complete` event ends the stream         |

- The transport reads a subscription through `fetch`, not `EventSource`, because `EventSource`
  cannot send the `Authorization` header.
- After a `401` response the transport calls `token(true)` once and sends the request again with the
  new token. A second `401` fails as `unauthenticated`.
- A request that takes longer than `timeout` is aborted and fails as `network`. The transport joins
  the timeout and the caller's signal with `AbortSignal.any`.

### Errors

```ts
/**
 * Lists the ways an operation fails.
 */
export type DataErrorKind =
  "conflict" | "forbidden" | "invalid" | "network" | "not-found" | "server" | "unauthenticated";

/**
 * Describes one value a service refused, as a form places it under its field.
 */
export interface DataIssue {
  /**
   * The service's code for the refusal, which a form translates like a schema keyword.
   */
  readonly keyword: string;

  /**
   * The service's own words, for development.
   */
  readonly message: string;

  /**
   * Path of the refused value, segment by segment.
   */
  readonly path: readonly (number | string)[];

  /**
   * Values the message reads, such as a limit.
   */
  readonly values: Readonly<Record<string, unknown>>;
}

/**
 * Reports why an operation failed.
 */
export class DataError extends Error {
  /**
   * Each refused value, for `invalid`. Empty for every other kind.
   */
  readonly issues: readonly DataIssue[];

  /**
   * The way the operation failed.
   */
  readonly kind: DataErrorKind;

  /**
   * Id of the operation that failed.
   */
  readonly operation: string;

  /**
   * The HTTP status, where a response arrived.
   */
  readonly status?: number | undefined;
}
```

The transport derives the kind from the first GraphQL error's `extensions.code`, and from the status
where the response contains no GraphQL error:

| Kind              | GraphQL code      | Status               | Retried             | Where it goes                                                             |
| ----------------- | ----------------- | -------------------- | ------------------- | ------------------------------------------------------------------------- |
| `network`         | none              | no response, timeout | Yes                 | The route's error component, or the mutation's caller                     |
| `unauthenticated` | `UNAUTHENTICATED` | 401                  | Once, after renewal | `onUnauthenticated`, which sends the person to sign in                    |
| `forbidden`       | `FORBIDDEN`       | 403                  | No                  | The caller, which states that the person may not do it                    |
| `not-found`       | `NOT_FOUND`       | 404                  | No                  | A route loader throws the router's `notFound()`, so the page is not found |
| `conflict`        | `CONFLICT`        | 409                  | No                  | The caller, which offers the current version. The record is invalidated   |
| `invalid`         | `BAD_USER_INPUT`  | 400, 422             | No                  | The form's fields, through `fieldErrorsOf`                                |
| `server`          | any other         | 429, 5xx, any other  | Yes                 | The route's error component, or the mutation's caller                     |

- An `invalid` error contains `issues` from the error's `extensions.issues`. `DataIssue` has the
  shape of `provider-form`'s `Issue` (`foundations/providers/form/src/issues.ts:17-38`), so a form
  places each issue under its field and translates its keyword as it translates a schema keyword:
  `<form>.errors.<path>.<keyword>`, then `errors.<keyword>`
  (`foundations/providers/form/src/identifiers.ts:74`).
- A form submits through its own submit validator, which runs the mutation and returns
  `fieldErrorsOf(error)` for an `invalid` refusal. TanStack Form puts the result on the fields.

```ts
/**
 * Returns a refusal's issues keyed by field path, as a form's submit validator returns them.
 */
export function fieldErrorsOf(error: unknown): FieldErrors | undefined;

/**
 * Lists a refusal's issues by the path of the field each one refuses.
 */
export interface FieldErrors {
  /**
   * The issue for each refused field.
   */
  readonly fields: Readonly<Record<string, DataIssue>>;
}
```

### The client

```ts
/**
 * Lists the changes one event of the changes stream reports.
 */
export interface ChangeBatch {
  /**
   * Each change, in the order the services made them.
   */
  readonly changes: readonly Change[];
}

/**
 * Describes data that arrived from the gateway for one query.
 */
export interface OperationData {
  /**
   * The data the gateway returned.
   */
  readonly data: unknown;

  /**
   * Id of the query's operation.
   */
  readonly operation: string;

  /**
   * The records the data contains, as the query stated them.
   */
  readonly resources: readonly ResourceSelector[];

  /**
   * The variables the query ran with.
   */
  readonly variables: Readonly<Record<string, unknown>>;
}

/**
 * Lists what a data client is created from.
 */
export interface DataClientOptions {
  /**
   * The subscription that streams changes to records. No stream where left out.
   */
  readonly changes?: Operation<ChangeBatch, NoVariables, "subscription"> | undefined;

  /**
   * Options over the foundation's defaults, in the library's form.
   */
  readonly defaultOptions?: DefaultOptions | undefined;

  /**
   * Called when a query's data arrives from the gateway, after a fetch or when the page hydrates
   * the server's data.
   */
  readonly onData?: ((arrival: OperationData) => void) | undefined;

  /**
   * Called when the gateway refuses the renewed token. The application sends the person to sign in.
   */
  readonly onUnauthenticated?: (() => void) | undefined;

  /**
   * The transport every operation runs through.
   */
  readonly transport: Transport;
}

/**
 * Creates the query client of one page, or of one request on a server.
 */
export function createDataClient(options: DataClientOptions): QueryClient;
```

The foundation's defaults, over the library's:

| Option                                                                | Value                                                             | Reason                                                                                                                  |
| --------------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `queries.queryFn`                                                     | Runs the operation the key names through the transport            | One fetcher serves every operation                                                                                      |
| `queries.staleTime`                                                   | 30 s                                                              | Hydrated data is not refetched at once. A change invalidates a record sooner                                            |
| `queries.retry`                                                       | Two retries, for `network` and `server` alone                     | A refused operation fails the same way again                                                                            |
| `mutations.retry`                                                     | One retry, for `network` alone                                    | The idempotency key makes the retry apply once                                                                          |
| `dehydrate.shouldDehydrateQuery`                                      | A query that succeeded, or that is pending with no failed attempt | The server writes no error into the page                                                                                |
| `queryCache.onError`, `mutationCache.onError`                         | Calls `onUnauthenticated` for `unauthenticated`                   | Every refusal of the session goes to one place                                                                          |
| `networkMode`, `gcTime`, `refetchOnWindowFocus`, `refetchOnReconnect` | The library's                                                     | A fetch waits while offline, unread data is removed after 5 minutes, and stale data refetches on focus and reconnection |

- `operationKey(operation, variables)` returns an operation's cache key,
  `["operation", id, variables]`. The first member keeps operations apart from any other query the
  application keeps.
- `createDataClient` keeps the transport for the client in a module `WeakMap`. A mutation reads it
  through the `client` its function receives (query-core 5.104.0,
  `build/modern/mutation.js:134-138`).

`createDataClient` subscribes to its query cache and calls `onData` for an operation's query when
its data arrives from the gateway:

| Arrival                                                 | Cache event                                           | Where the library sends it (query-core 5.104.0)                         |
| ------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------- |
| A fetch succeeds                                        | `updated`, whose action is `success` without `manual` | `build/modern/query.js:86-95, 392`                                      |
| The page hydrates a query the cache lacks               | `added`, with the query's data already in its state   | `build/modern/hydration.js:144-157`, `build/modern/queryCache.js:64-72` |
| The page hydrates newer data into a query the cache has | `updated`, whose action is `setState` with data       | `build/modern/hydration.js:130-143`                                     |

- The query cache's `onSuccess` runs after a fetch alone (`build/modern/query.js:392-393`), so it
  would miss every query the page hydrates.
- `setQueryData` marks its write `manual` (`build/modern/queryClient.js:190-193`), so `onData` never
  receives an optimistic patch as data from the gateway.
- The cache calls its listeners synchronously, inside its notification batch
  (`build/modern/queryCache.js:191-197`). `onData` returns nothing, and a reader that needs
  asynchronous work starts it itself.

`DataProvider` renders the client for the tree and runs the changes stream while it is mounted:

```tsx
<Shell app="people">
  <DataProvider client={client}>
    <RouterProvider router={router} />
  </DataProvider>
</Shell>
```

### Queries

```ts
/**
 * Types an operation's cache key: `["operation", id, variables]`.
 */
export type OperationKey = readonly ["operation", string, object];

/**
 * Lists what a query states beside its operation and variables.
 */
export interface OperationQueryOptions<Data, Selected> {
  /**
   * The records the data contains, which invalidation by resource reads.
   */
  readonly resources?: readonly ResourceSelector[] | undefined;

  /**
   * Derives what a component reads from the data, such as a filtered and ordered list.
   */
  readonly select?: ((data: Data) => Selected) | undefined;

  /**
   * Milliseconds the data is fresh, or `"static"` for data that never changes.
   */
  readonly staleTime?: number | "static" | undefined;
}

/**
 * Types the options `operationQuery` builds, which are the options the library's `queryOptions`
 * returns for the operation's key.
 */
export type OperationQuery<D, S> = UnusedSkipTokenOptions<D, DataError, S, OperationKey> &
  QueryKeyWithDataTag<OperationKey, D, DataError>;

/**
 * Builds the library's query options for one operation and its variables.
 */
export function operationQuery<Data, Variables extends object, Selected = Data>(
  operation: Operation<Data, Variables, "query">,
  variables: Variables,
  options?: OperationQueryOptions<Data, Selected>,
): OperationQuery<Data, Selected>;
```

A component reads with the library's hooks over those options:

```tsx
const { data: request } = useSuspenseQuery(
  operationQuery(requestById, { id }, { resources: [REQUEST] }),
);
```

- Components that ask for the same operation and variables share the key, so they share one request
  and one cache entry.
- `operationQuery` puts the resource selectors in the query's `meta`. The library dehydrates `meta`
  with the data (query-core 5.104.0, `build/modern/hydration.js:48`) and restores it (`:149`), so
  invalidation by resource works on a hydrated query too.
- A list the page filters and orders in the browser is a query with `select`. A list the service
  filters, orders or pages is a query whose variables contain the filter, the order and the page.
- `operationInfiniteQuery(operation, variables, { initialPage, nextPage })` builds the library's
  infinite query options for a list read one page at a time, with the page in the variables.

### Resources

A resource is one record the services keep, named by its kind and its id. A query states where its
data contains records, so a change to a record invalidates every query whose data shows it.

```ts
/**
 * Names one record: its kind's qualified id and its id.
 */
export interface ResourceRef {
  /**
   * Id of the record within its kind.
   */
  readonly id: string;

  /**
   * Qualified id of the resource kind: `time-off/request`.
   */
  readonly type: string;
}

/**
 * States where a query's data contains records of one kind.
 */
export interface ResourceSelector {
  /**
   * Dotted path of the records in the data. The data itself where left out.
   */
  readonly at?: string | undefined;

  /**
   * Member of each record that contains its id.
   */
  readonly id: string;

  /**
   * True where the records form a list that a created record of the kind may join.
   */
  readonly list?: true | undefined;

  /**
   * Qualified id of the resource kind.
   */
  readonly type: string;
}
```

```ts
const REQUESTS: ResourceSelector = {
  at: "requests.items",
  id: "id",
  list: true,
  type: "time-off/request",
};
```

- The value at `at` is one record or an array of records. A record lacking the `id` member is
  skipped.
- A resource kind's qualified id is the one a plugin declares for access checks (RFC-0014), so one
  id names a record in a permission check, in a query's data and in a change.

### Changes and invalidation

```ts
/**
 * Describes a change to one record.
 */
export interface Change extends ResourceRef {
  /**
   * What happened to the record.
   */
  readonly action: "created" | "deleted" | "updated";
}

/**
 * Invalidates every query whose data a change may make stale, and refetches the active ones.
 */
export function invalidateChanges(client: QueryClient, changes: readonly Change[]): Promise<void>;
```

| Change               | Invalidates                                                             |
| -------------------- | ----------------------------------------------------------------------- |
| `updated`, `deleted` | Every query whose selectors find a record with the change's kind and id |
| `created`            | Every query with a `list` selector of the change's kind                 |

- `invalidateChanges` calls the library's `invalidateQueries` with a predicate, so active queries
  refetch at once and inactive ones refetch when a component reads them again (query-core 5.104.0,
  `build/modern/hydration-B9t5w6NC.d.ts:1448-1461`).
- A change contains ids alone. The refetch runs the operation through the gateway, which checks the
  person's access again.

The client learns of changes from these sources:

1. A mutation, through the changes it states (see "Mutations").
2. The changes stream. `DataProvider` runs the `changes` subscription while it is mounted, and each
   event's data is a `ChangeBatch`.
3. The application, which calls `invalidateChanges` for a change it learns of another way.

The stream runs in the browser alone, and reconnects after it drops: after 1 s, then twice as long
each time up to 30 s, each wait varied by up to 20%. After it reconnects, the client invalidates
every active query, because the changes made while it was down never arrived.

### Mutations

```ts
/**
 * Lists what a mutation states beside its operation.
 */
export interface OperationMutationOptions<Data, Variables> {
  /**
   * The records the mutation changes, invalidated once it settles.
   */
  readonly changes?:
    ((variables: Variables, data: Data | undefined) => readonly Change[]) | undefined;

  /**
   * The patches to apply at once to every query whose data contains a patched record.
   */
  readonly optimistic?: ((variables: Variables) => readonly RecordPatch[]) | undefined;

  /**
   * Scope whose mutations run one at a time, in the order they started, such as the record's id.
   */
  readonly scope?: ((variables: Variables) => string) | undefined;
}

/**
 * States how one record looks after a change.
 */
export interface RecordPatch extends ResourceRef {
  /**
   * Returns the record after the change, or undefined where the change removes it.
   */
  readonly apply: (
    record: Readonly<Record<string, unknown>>,
  ) => Record<string, unknown> | undefined;
}

/**
 * Types the variables the library runs a mutation with: the caller's variables and the key that
 * makes a retry apply once.
 */
export interface KeyedVariables<Variables> {
  /**
   * Key the transport sends as `Idempotency-Key`, the same on every retry.
   */
  readonly idempotencyKey: string;

  /**
   * The caller's variables.
   */
  readonly variables: Variables;
}

/**
 * Types the library's result of a mutation that runs with keyed variables.
 */
type KeyedResult<D, V> = UseMutationResult<D, DataError, KeyedVariables<V>>;

/**
 * Types the options one call of `mutate` takes.
 */
export type OperationMutateOptions<D, V> = MutateOptions<D, DataError, KeyedVariables<V>>;

/**
 * Lists the members of the library's result that `useOperationMutation` replaces.
 */
type Replaced = "mutate" | "mutateAsync";

/**
 * Types what `useOperationMutation` returns. `mutate` and `mutateAsync` take the caller's variables.
 */
export type OperationMutationResult<D, V> = DistributiveOmit<KeyedResult<D, V>, Replaced> & {
  readonly mutate: (variables: V, options?: OperationMutateOptions<D, V>) => void;
  readonly mutateAsync: (variables: V, options?: OperationMutateOptions<D, V>) => Promise<D>;
};

/**
 * Runs a mutation, with a fresh idempotency key for each call and the same key on its retry.
 */
export function useOperationMutation<Data, Variables extends object>(
  operation: Operation<Data, Variables, "mutation">,
  options?: OperationMutationOptions<Data, Variables>,
): OperationMutationResult<Data, Variables>;
```

```tsx
const approve = useOperationMutation(approveRequest, {
  changes: ({ id }) => [{ action: "updated", id, type: "time-off/request" }],
  optimistic: ({ id }) => [
    { apply: (request) => ({ ...request, status: "approved" }), id, type: "time-off/request" },
  ],
});
```

A mutation with `optimistic` runs the library's optimistic update in five steps (see "References"):

1. It cancels the fetches of every query whose data contains a patched record.
2. It keeps a copy of each of those queries' data.
3. It writes each query's data with the patched records, through the query's resource selectors.
4. Where the service refuses, it writes the copies back and rejects with the `DataError`.
5. Once it settles either way, it invalidates the patched records and the stated `changes`.

- A patch applies to every query whose data contains the record, so a list row and a detail page
  change together.
- A created record is not patched in, because its place in a list is the service's to decide. The
  page shows the pending creation through the library's `useMutationState` until the list refetches.
  A pending mutation's `variables` there are its `KeyedVariables`.
- `useOperationMutation` generates the idempotency key with `crypto.randomUUID()` when `mutate` is
  called, and passes the library the key beside the variables. The library runs every retry with the
  same variables object (query-core 5.104.0, `build/modern/mutation.js:139-143`), and resumes a
  paused mutation with them (`:97-99`), so every attempt sends the same key.
- A mutation states the record's version in its variables where the service checks versions. A stale
  version is refused as `conflict`, and the record is invalidated so the page shows the current one.
- Mutations with the same `scope` run one at a time (query-core 5.104.0,
  `build/modern/hydration-B9t5w6NC.d.ts:2645-2650`). A record's own changes then arrive in the order
  the person made them.

### Offline

- A fetch made while offline waits, and a mutation made while offline is paused. The client sends
  the paused mutations, in order, once the page is online or focused again (query-core 5.104.0,
  `build/modern/queryClient.js:52-60, 455-456`).
- `useNetwork()` returns `{ online, paused }`: whether the page is online, and how many mutations
  are waiting. A product's frame renders the offline state from it, in `AppShell.Status` for a
  product composed from plugins (RFC-0013).
- A paused mutation is lost when the page reloads, until persistence exists (see "Unresolved and
  future work").

### A change of person or tenant

```ts
/**
 * Cancels every fetch and mutation, and removes all cached data and every paused mutation.
 */
export function resetData(client: QueryClient): Promise<void>;
```

- The application calls `resetData` when the signed-in person or the tenant changes. The plugin host
  calls it in the same step as it moves the settings to the new subject's keys (RFC-0014).
- A paused mutation is removed rather than sent, because it would run with the next person's token.
- The cache keys contain no tenant. A reset removes all data of the previous subject, so none of it
  can render.

### Route loaders

`provider-router`'s declaration gains a loader, which the compiler turns into the route's `loader`
with the search as its dependencies:

```ts
/**
 * Lists what a declared route's loader receives.
 */
export interface RouteLoaderArgs {
  /**
   * The router's context, which contains the data client.
   */
  readonly context: unknown;

  /**
   * The route's parameters.
   */
  readonly params: Readonly<Record<string, string>>;

  /**
   * True where the router loads the route ahead of a navigation.
   */
  readonly preload: boolean;

  /**
   * The route's validated search.
   */
  readonly search: unknown;

  /**
   * Signal that aborts when the navigation is superseded.
   */
  readonly signal: AbortSignal;
}

/**
 * Loads a route's data before its page renders.
 */
export type RouteLoader = (args: RouteLoaderArgs) => Promise<void> | void;
```

The `./router` entry states the router's context and builds loaders from data needs:

```ts
/**
 * Lists what the router's context contains in an application with data.
 */
export interface DataContext {
  /**
   * The page's data client.
   */
  readonly data: QueryClient;
}

/**
 * States one query a page reads, and the names its variables take from the route.
 */
export interface DataNeed {
  /**
   * The query.
   */
  readonly operation: Operation<unknown, object, "query">;

  /**
   * The records its data contains.
   */
  readonly resources?: readonly ResourceSelector[] | undefined;

  /**
   * Names of the variables, each read from the route's parameters, then from its search.
   */
  readonly variables?: readonly string[] | undefined;
}

/**
 * Builds a route loader that loads every need of a page in parallel.
 */
export function loadNeeds(needs: readonly DataNeed[]): RouteLoader;
```

- On a navigation the loader awaits `client.query(options)` for each need with
  `staleTime: "static"`. Cached data renders at once, and stale data refetches in the background
  when the page reads it. The library deprecates `ensureQueryData` for this call (query-core
  5.104.0, `build/modern/hydration-B9t5w6NC.d.ts:1337`).
- On a preload it starts each fetch and returns without waiting, and a failure is left for the
  navigation to report.
- A `not-found` refusal throws the router's `notFound()`, so a record the person may not read, or
  that does not exist, renders the not-found page.
- A variable that neither the parameters nor the search contain throws, naming the route and the
  variable.
- The router's `defaultPreloadStaleTime` is 0 (`foundations/providers/router/src/defaults.ts:22`),
  so a preload always calls the loader, and the client's freshness decides whether it fetches.

An application that writes its own routes writes the loader in the library's form:

```ts
const request = createRoute({
  getParentRoute: () => requests,
  loader: ({ context, params }) =>
    context.data.query(operationQuery(requestById, { id: params.id })),
  path: "$id",
});
```

### On a server

```ts
/**
 * Connects the data client to the router, so the server's data streams into the page and a query
 * that throws the router's `redirect` navigates.
 */
export function setupDataIntegration(options: DataIntegrationOptions): void;

/**
 * Lists what the data integration connects.
 */
export interface DataIntegrationOptions {
  /**
   * The request's data client.
   */
  readonly client: QueryClient;

  /**
   * The request's router.
   */
  readonly router: AnyRouter;
}
```

- Each request creates its own data client, with a gateway transport over the request's token, and
  puts it in the router's context. The data of one request never renders in another.
- `setupDataIntegration` calls `setupRouterSsrQueryIntegration` of
  `@tanstack/react-router-ssr-query` with `wrapQueryClient: false`, because `DataProvider` renders
  the client. The integration dehydrates the queries the render read, pending ones included, streams
  each query that settles later, and hydrates them in the browser in the same order
  (`@tanstack/router-ssr-query-core` 1.169.3, `dist/esm/index.js:30-131`).
- The integration wraps the caches' `onError` for redirects and calls the foundation's for every
  other error (`dist/esm/index.js:132-155`), so `onUnauthenticated` still applies. The application
  creates the client before it calls `setupDataIntegration` for that reason.
- The integration dehydrates every query the client's `dehydrate.shouldDehydrateQuery` accepts
  (`dist/esm/index.js:39`). The library copies a query's state as it is, its error included
  (query-core 5.104.0, `build/modern/hydration.js:38-51`), so the foundation's default leaves out a
  query that failed or is retrying. A query that fails after the render has its error replaced by
  `Error("redacted")` (`build/modern/hydration.js:19-27`).
- The changes stream starts in the browser after hydration.

### Tests and development

The `./testing` entry serves operations from samples:

```ts
/**
 * Serves one operation with data, with a function of its variables, or with a refusal.
 */
export type Sample =
  | { readonly data: unknown }
  | { readonly error: DataError }
  | { readonly respond: (variables: Readonly<Record<string, unknown>>) => unknown };

/**
 * Creates a transport that serves each operation from its sample, and refuses an operation without
 * one.
 */
export function sampledTransport(samples: Readonly<Record<string, Sample>>): Transport;

/**
 * Creates a client for a test, which never retries or streams changes and keeps data until the test
 * ends.
 */
export function createTestDataClient(transport: Transport): QueryClient;
```

- An operation without a sample fails with this message, so a test cannot pass on data it never
  stated: `The sampled transport has no sample for time-off~4~9c1e7a.`
- A test that changes a record calls `invalidateChanges` itself, because the sampled transport
  streams nothing.
- An application runs in development on a sampled transport until its gateway exists.

### The boundary

- The foundation does not know sessions. The application passes the token and the reset.
- The foundation does not know permissions. The plugin host reads each query's data through `onData`
  (RFC-0020).
- The foundation does not validate data. The gateway's schema types it.

## Failure handling

| Failure                                                | Detected by                 | Outcome                                                                               |
| ------------------------------------------------------ | --------------------------- | ------------------------------------------------------------------------------------- |
| The gateway is unreachable, or a request times out     | The transport               | `network`. A query retries twice, a mutation once, then the caller receives the error |
| The token expired                                      | The transport               | One renewal and one retry. Then `unauthenticated` and `onUnauthenticated`             |
| A record does not exist, or the person may not read it | The gateway                 | `not-found`. A loader renders the not-found page                                      |
| A change conflicts with a newer version                | The gateway                 | `conflict`. The optimistic change is written back, and the record is invalidated      |
| A form's values are refused                            | The gateway                 | `invalid`. `fieldErrorsOf` puts each issue under its field                            |
| The page goes offline                                  | The library                 | Fetches wait, mutations pause, and both resume once the page is online                |
| The changes stream drops                               | `DataProvider`              | Reconnects after 1 s up to 30 s, then invalidates every active query                  |
| A query fails during a server render                   | The client's dehydrate rule | The query is left out of the page, and the browser fetches it again                   |
| The person or the tenant changes                       | The application             | `resetData` removes all cached data and every paused mutation                         |
| An operation has no sample in a test                   | The sampled transport       | The operation fails, naming its id                                                    |
| A loader's variable is missing from the route          | `loadNeeds`                 | Throws, naming the route and the variable                                             |

## Bounds

- TanStack Query's client, its provider, `useQuery`, `useMutation`, `dehydrate` and `hydrate` bundle
  to 11.3 kB gzipped (esbuild, minified, React external, `@tanstack/react-query` 5.104.0, measured
  2026-09-30). The foundation's own code is not measured yet.
- One request per operation and variables at a time, however many components read them.
- An invalidation walks every cached query once and reads the records at each of its selectors.
- `onData` runs once per arrival of a query's data.
- One changes stream per tab.
- A request fails after 30 s. A query tries three times at most, a mutation twice.

## Alternatives considered

### TanStack DB for whole lists in the browser

Collections that keep a list's rows, apply changes to them optimistically, and run live queries with
joins in the browser.

**Why not now:** `@tanstack/db` 0.9.2 calls itself beta, published 16 releases in the 90 days before
2026-09-14, and a caret range over a 0.x version does not admit a new minor. It adds 87.5 kB gzipped
to an application that bundles TanStack Query. A list the page filters and orders is a query with
`select`, and an optimistic change applies to every query's data through the resource selectors. Its
1.0 release is the time to measure again.

### A GraphQL client

urql or Relay, with a normalised cache.

**Why not:** the browser sends persisted operations by id and never parses a document. TanStack
Query is already the cache, and the router integrates with it. A normalised cache needs the schema's
keys in the browser, and invalidation by resource keeps every query that shows a record current.
urql adds 11.0 kB gzipped and Relay 56.4 kB, measured with the same bundling.

### The router's loader data as the cache

Each route's loader returns its data, and the page reads it with `useLoaderData`.

**Why not:** it adds a second cache with a second freshness rule. Two routes that read one record
would keep two copies, and a mutation would have to update both. The router already leaves freshness
to the query client.

### Records in the changes stream

The stream contains each changed record, and the client writes it into the cache.

**Why not:** the stream would deliver records to every subscriber without the access check that
running the operation applies per person. With ids alone the stream contains nothing a person may
not read, and the refetch runs the checked operation.

### The tenant in every cache key

**Why not:** the keys would keep one tenant's data apart from another's, and a switch back would
reuse it. A reset removes the paused mutations as well, which a key cannot do, and frees the memory.
The cost is a refetch after a switch back.

### Data validated at run time

A Standard Schema per operation, run on every response.

**Why not:** the gateway's schema types every response, and generated types check the reader at
build. A validator costs its bytes in the bundle and its time on every response.

### The library under names of the foundation's own

**Why not:** a second vocabulary over TanStack Query would be a second API to learn and to keep in
step with the library's releases. The foundation adds operations, the transport and resources, and
leaves the library's names as they are.

## Drawbacks

- TanStack Query deprecates methods within a major version: 5.102.0 deprecated `ensureQueryData` in
  favour of `query()`. The foundation follows the library's current API.
- A query that states no resource selectors is refreshed only by staleness, focus, reconnection and
  explicit invalidation.
- A change contains ids alone, so it costs a refetch of every active query that shows the record.
- A query that failed during a server render is fetched again in the browser.
- A mutation made offline is lost when the page reloads, until persistence exists.
- Operation types are written by hand until codegen exists, and can drift from the gateway's schema.

## Unresolved and future work

- Types and operation modules generated from the gateway's schema and the published documents. The
  first schema brings it in.
- The pipeline that publishes a product's documents to the gateway before the product goes live.
- Persisting cached data and paused mutations across a reload, with the library's persisters at
  5.104.0.
- A transport for a service the browser calls outside the gateway.
- TanStack DB, measured again at its 1.0 release, for live queries across lists.
